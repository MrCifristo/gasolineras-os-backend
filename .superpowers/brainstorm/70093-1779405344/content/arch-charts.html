¿Quién renderiza las gráficas?

Esta es la decisión arquitectónica clave — cambia cómo frontend y backend se coordinan

A

Frontend renderiza → captura → envía al backend

Flujo: El usuario ve las gráficas en el sitio con Recharts/Chart.js. Al hacer clic en "Descargar PDF", el frontend exporta cada gráfica como imagen PNG/SVG (con html2canvas o el método nativo de la librería), las empaqueta junto con los filtros activos y hace un POST /api/v1/reportes/pdf con todo eso en el body. El backend recibe las imágenes, las inserta en el HTML template, Puppeteer renderiza y devuelve el PDF.

✓ Las gráficas del PDF son exactamente las mismas que ve el usuario — mismo color, mismo estilo, misma librería
✓ No hay duplicación de lógica de gráficas entre frontend y backend
✓ Backend solo maneja layout del PDF y datos tabulares — clara separación de responsabilidades
⚠ El frontend necesita implementar la lógica de captura (html2canvas o similar) antes de que exista el endpoint del PDF
⚠ El POST puede ser pesado si hay muchas gráficas en base64 — mitigable con compresión PNG

B

Backend renderiza sus propias gráficas independientemente

El frontend y el backend tienen gráficas separadas. El usuario hace clic en "Descargar PDF" y el frontend hace un GET /api/v1/reportes/pdf?... pasando solo los filtros. El backend genera los datos, construye las gráficas como SVG propio, Puppeteer renderiza todo y devuelve el PDF.

✓ Más simple de integrar desde el frontend — solo un GET con query params
✓ Backend completamente autónomo, funciona sin que exista el frontend
✗ Las gráficas del PDF lucen diferentes a las del frontend — doble esfuerzo de diseño
✗ Si cambias colores o tipos de gráfica en el frontend, el PDF queda desactualizado automáticamente
✗ Duplicas lógica de gráficas — la mantienes dos veces

C

Puppeteer navega directamente la página del frontend ⚡

El backend lanza Puppeteer, navega a una ruta especial del frontend (ej. http://frontend/reportes/print?token=...&filtros=...), espera a que las gráficas terminen de renderizar, y "imprime" esa página a PDF. El PDF es literalmente una foto de la UI real.

✓ PDF = exactamente la UI, sin trabajo extra de exportación
✓ Una sola fuente de verdad para el diseño visual
✗ El backend necesita acceso de red al frontend en tiempo de ejecución — problema en producción si están en servidores distintos
✗ Pasar el JWT de auth al Puppeteer es delicado y riesgoso
✗ Más frágil — si el frontend tarda en cargar, el PDF falla

💡 Mi recomendación: A — el frontend captura y envía las gráficas.
Las gráficas del PDF serán idénticas a la UI, no se duplica lógica, y el contrato entre frontend y backend es claro: POST /reportes/pdf con { filtros, graficas: { donut, linea, vehiculos, pilotos } }. El único costo es implementar la captura con html2canvas en el frontend — cosa que de todas formas necesitarías si quisieras un "botón de compartir captura".
